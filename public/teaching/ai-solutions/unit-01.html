AI capabilities and useful tasks

Which AI capability fits a real need, and how will a person check it?

Learn

By the end of this unit

  • Match a concrete task to an AI capability, permitted inputs, and useful output.
  • Choose a practical no-code route and inspect a supplied output for a consequential error.
  • Distinguish a candidate output, verified evidence, and an authorized action.

iExplain

Begin with the work someone needs done

AI can help with a personal task, a community service, creative work, research, or an organizational process. Start with the person and intended result. “Use AI” is not a task. “Turn permitted event notices into a checked dates-and-locations table” is a task you can try and evaluate. No prior AI, programming, statistics, or business study is required; we introduce concepts when you need them.

A capability map: from a need to something usable

A capability is a kind of work an AI tool may support. Availability depends on the selected tool, input format, access, and settings. One tool may combine capabilities; do not assume it supports every row. The following are original learning examples, not verified performance claims.

Seven AI capabilities, possible applications, and no-code implementation choices
CapabilityNeed → possible outputNo-code route and essential check
Generate or transform textA volunteer needs a short version of a long approved notice → a plain-language draft.Give an available assistant the permitted text, audience, and format; compare the draft with the original for lost conditions and invented details.
Answer from sourcesA researcher or participant needs an answer within a document set → an answer with source passages, or “not supplied.”Provide approved passages in a document or suitable source-aware assistant; verify that the passages actually support each material claim.
Extract or classifyA community group needs event details organized → a table of dates, places, and missing fields; requests may also be sorted into defined categories.Specify columns or categories in a prompt or visual tool; check every field against the input and test ambiguous cases. A guessed date is not a completed record.
Analyze data or predictA project organizer needs to understand attendance → a summary, chart, or conditional estimate for the next session.Use an approved spreadsheet or visual analysis tool with suitable data; recalculate totals, compare with a simple baseline, and test estimates on held-out or later observations. A chatbot's plausible number is not a validated prediction.
Interpret or create imagesA creative project needs concepts or an image description → candidate illustrations or a proposed description.Use a suitable image-capable tool with permitted inputs; inspect factual details, required text, accessibility, and permission to use the material. Do not treat a generated scene as a photograph of an event.
Transcribe, translate, or speakA group needs an accessible version of a permitted recording or notice → a transcript, translation, or spoken draft.Use a tool that supports the required language or audio task; compare names, numbers, meaning, and missing sections with the original. Obtain permission before using another person's recording.
Coordinate a workflow or agentA team needs requests prepared for review → information is collected, a draft is prepared, and exceptions are routed.Use a checklist or visual workflow with explicit handoffs. A workflow follows specified steps; an agent can select actions within its given tools and permissions. Test stop rules and keep consequential actions under the responsible person's control.

One continuing case makes the process concrete

Cedar Desk needs an accurate, useful reply to a booking question. Its ReplyKit combines source-grounded answering and text drafting inside a human-reviewed workflow. The coordinator finds the policy, checks conditions, and avoids promising an action that has not happened. The same pattern can support an equipment-loan service, a community information desk, or a research-document helper; your one capstone can address an appropriate need from any discipline.

You can operate a useful solution with working documents, a spreadsheet, an available AI tool, or a visual no-code tool. A supplied-output route lets you inspect the same decision without an AI account: label its AI step simulated using a supplied output. It does not establish that you connected a live model or automated a process. Both routes still need usable inputs, a check, an output or handoff, and an observed user task.

A bounded instruction you can copy and improve
Using only sources S1–S6 in the Cedar Desk packet, prepare a concise reply to this fictional booking question. List the source for each material claim. If a needed fact is missing, ask for it. Do not promise availability, policy exceptions, or actions already completed. Return a draft, a source table, and any item needing human review.

This specifies a task, evidence boundary, audience, format, and stop condition. It does not guarantee correctness. Save the original output and your checks.

The AI Fluency Framework — short guide

Open the short guide here. Identify one decision about delegation, one instruction, one output check, and one responsibility in your task. No account or external PDF reader is needed for this course explanation.

Read the short guide here

Four habits for working with AI. This original course explanation applies the AI Fluency Framework to your project; it is not a reproduction of the publisher's one-page guide.

Delegation — choose the work
Decide whether AI is useful for this task, which step it may assist, and which decisions a person must retain.
Description — make the task clear
Give the permitted inputs, goal, audience, output format, constraints, and a clear stopping rule.
Discernment — inspect the result
Compare the output with sources and success criteria. Check for missing conditions, invented claims, and whether it helps complete the intended task.
Diligence — remain responsible
Own the decision to use or release the result. Protect information, disclose material AI assistance, and arrange human review or escalation where needed.

Apply to your task: Write one AI-assisted step, one instruction, one output check, and one responsibility you keep. Use your existing project record; this is optional practice, not another submission.

Choose a capability, then inspect its output

Before opening the worked answer, select a first capability for each task: (A) turn two event notices into dates and locations; (B) answer a question from approved policy passages; (C) describe weekly attendance and consider a next-week estimate. Name the input, output, and one check. More automation is not automatically a better choice.

Task and permitted inputSupplied candidate outputYour decision
A — ExtractionNotice 1: “Repair meetup, 12 May, Library Room 2.” Notice 2: “Garden exchange, 15 May; location to follow.” Candidate: Repair / 12 May / Room 2; Garden / 15 May / Room 2.Which field is unsupported? What should replace it?

Compare your capability choices and checks

A: Extract stated fields into a table; the second location is missing, not Room 2. Preserve “not supplied” and ask the owner if needed. B: Source-grounded answering can prepare a conditional reply, but no availability, destination, or completed action is established. Ask which session to check. C: Simple analysis gives (18 + 20 + 19 + 23) ÷ 4 = 20. A mean is not proof of next week's attendance. Four counts and a confident sentence do not validate a forecast; begin with a simple baseline and define a future check before making commitments.

Repair ReplyKit's unsupported answer

For the 60-hour booking request, the supplied AI draft says: “Your place has been moved, and there is no charge. Your new session is confirmed.” Mark each claim supported, unsupported, or unknown. Write a revised reply and its source/claim table before revealing the explanation.

Worked review

The timing meets S3, but space and the requested destination are unknown. No booking action occurred. “Moved,” “no charge,” and “confirmed” are unsupported. A sound revision is: “A change can be considered because your session is at least 48 hours away. It depends on available space and coordinator confirmation. Which session would you like us to check? Your booking has not yet been changed.”

Now change the request to 20 hours. The 48-hour rule no longer applies: prepare owner review. Varying a consequential fact tests whether the solution follows the source rather than repeating fluent wording.

Your continuing case: Cedar Desk

Fictional teaching case. Cedar Desk is a booking and customer-support service for small workshop businesses. Its coordinators answer questions about bookings, cancellations, rescheduling, and special requests. The operations owner wants dependable replies without unnecessary checking or repeated clarification. Your project is ReplyKit: a small source-grounded reply service that turns a permitted question into a checked response or a useful human handoff. It can run with documents, a calculator, and an available AI assistant or the supplied draft. No application or live customer account is needed.

The user is a booking coordinator. The responsible decision owner is the operations owner. A customer receives the final approved reply. Those are three different roles. The owner has agreed only to a classroom exploration in this fictional case, not to a purchase, a live integration, or a commercial launch. Your instructor may replace this packet with an approved partner brief while preserving the same tasks and evidence standards.

Discovery packet

Eight supplied, fictional interview records describe waits of 4, 5, 5, 6, 6, 7, 8, and 31 minutes for a response. Six of eight describe repeated delay; three of eight say they would try a pilot. These convenience-case records are teaching inputs, not a representative market survey. They do not establish purchase intent. Response waiting time is different from the staff processing time in the later benchmark.

  • Coordinator: “I often know the basic answer. Finding the latest policy and asking about exceptions takes longer.”
  • Customer: “My last reply was quick, but I still did not know whether the date change was confirmed.”
  • Owner: “I might try a small test if I can inspect every reply. I have not approved a budget.”
  • Contrary evidence: Two of the eight records report no repeated delay. One of these customers prefers a clear policy page to another conversation.

These are invented case statements, not quotations from real people. In a discovery role-play, the respondent uses the card and says “unknown” when the packet does not answer a question. A complete usable example

Intake: Case 5; request to move a booking 60 hours before the session. Sources: S3, S4, S6. Draft: “Your request is at least 48 hours before the session, so a change can be considered. It depends on available space and coordinator confirmation. Which session would you like us to check? Your booking has not yet been changed.” Review: Timing, conditional wording, missing desired session, and no false confirmation checked. Handoff: A coordinator checks availability and confirms or declines the requested change. Status: Approved draft for classroom use; no external message sent.

Start one project record and make a capability choice

Use ReplyKit or choose one appropriate personal, community, creative, research, or organizational need. Create one project record with five sections: need and evidence; solution and workflow; tests and revision; impact and adoption; operation and handoff. Keep this project throughout the course.

  1. Write the intended user, task, and useful result in one sentence.
  2. Select one primary capability from the map. Compare it with one other capability or a simpler non-AI method. Explain why the input and output fit your choice.
  3. Record permitted inputs, expected output, available no-code execution route, a likely failure, and the human check or stop condition. Name a responsible decision owner; for an appropriate personal task, this can be you.
  4. Save a supplied or actual AI output, your correction, and a source or calculation check. Label an actual tool and version when known; label supplied outputs and the simulated AI step honestly.
  5. Write one uncertainty about the underlying need. Do not invent an interview, a tool connection, or a successful use to resolve it.

For ReplyKit, choose source-grounded answering plus drafting; use the source card, bounded instruction, draft, and review table above. Another project may need extraction, images, speech, data analysis, or a bounded workflow instead. Use only permitted information and capabilities your available tool supports.
